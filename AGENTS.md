# AGENTS.md

## Project Philosophy

`Kirakira` is a lightweight, high-performance, modern KRKR game emulator. It targets KRKR2/KRKRZ compatibility and full cross-platform reach across Linux, macOS, Windows, Android, iOS, and Web without C++ glue code.

## Architecture

- `krkr-tjs2`: TJS2 language frontend, compiler, bytecode VM, object model, and language builtins. Includes an interactive debugger core (`debug` module: source-line breakpoints, stepping, exception breaks, pause/inspect context) driven by a `DebugUi` implementation; MIR emits per-statement `SourceMark` instructions so bytecode carries statement-level source positions. Includes a `decompile` module: a pattern-matching TJS2 bytecode decompiler (the frontend `printer` renders the reconstructed `syntax::Program`) that rebuilds structured statements (if/while/do-while/for/break/continue/try/switch, `&&`/`||` chains and their value forms, `?:` ternaries, in-place function literals, class/property registrations) from the official compiler's and krkr's own compiler's emission patterns over a block CFG with dominance-based back-edge detection, and degrades unmatchable fragments to `// <unhandled: ...>` comments instead of failing. A seeded syntax fuzzer (`decompile/fuzz.rs`) round-trips generated programs (compile -> decompile -> reparse -> recompile -> execute both with a hard timeout) and asserts the failure count never grows past the recorded baseline; validated against real game bytecode (krkr-decomp `--verify` over a full game's XP3 archives).
- `krkr-kag`: KAG parser and scenario control flow. It handles labels, tags, macros, conditionals, script blocks, jump/call/return, parser snapshots, and host callbacks.
- `krkr-engine`: KRKR/TVP engine runtime. It owns the TJS runtime and KAG parser, registers TVP globals/native objects, coordinates project storage, XP3 access, layers, transitions, timers/events, audio commands, and pure Rust plugin registration. Checks KAG line/label breakpoints before each scenario tag via the tjs2 debugger. Implements the native `VideoOverlay` object (`native/video.rs`): movies decode on a per-overlay thread through krkr-video (video frames and soundtrack chunks are pumped together with bounded-channel back-pressure), playback runs on the host clock, the soundtrack streams to krkr-audio as live PCM (`PlayPcmStream`), and the engine tick fires the TJS status events (`ready`/`play`/`pause`/`stop`/`unload`, `onPeriod`) KAG movie conductors wait on; visible overlays present as top-most texture quads in the frame output. Layer drawing follows the official `tTJSNI_BaseLayer` contracts: `native/blend.rs` ports `GetBltMethodFromOperationModeAndDrawFace` (`LayerIntf.cpp:3791`) with every `om*` operation mode and the PS blend family plus the `Blt` `hda`/opacity variants, and every blit family (`copyRect`, `operateRect`, `fillRect`, `colorRect`, `stretchCopy`/`operateStretch`, `affineCopy`/`operateAffine`, `piledCopy`) resolves `holdAlpha`, draw faces, `ClipRect` (`setClip`/`ResetClip`), `neutralColor`, pixel accessors and `TVPToActualColor` the way the reference implementation does. A blit target whose image was freed throws `Not drawable layer type` instead of allocating one (`PiledCopy`/`CopyRect`/`*Stretch`/`*Affine`, `LayerIntf.cpp:4111-4453`), `Layer.convertType` rewrites the stored image between the straight-alpha and premultiplied representations per `ConvertLayerType` (`:1703-1727`), and `piledCopy` builds its pile over transparency with `BltImage`'s per-child rules before copying it plane-for-plane (`:4102-4142`, `:5164-5364`) — the child's `DisplayType` picks the blt, the pile's layer type picks the `OnAlpha`/`hda` variants, and `ltBinder` children draw nothing. Stretch/affine blits honour the `st*` interpolation types (kernels ported from `visual/gl/WeightFunctor.h`; the filtered stretch path reuses the reference resampler's tap windows, edge fold and shrink-widened kernel, `visual/gl/ResampleImage.cpp:232-368`), the affine blit samples the source rectangle in the reference's `-0.5` corner frame (`LayerBitmapIntf.cpp:2711-2718`, `:3494-3513`), and `Window.setZoom` maintains the official inner-size/paint-box split. Layer images follow the official `MainImage` semantics too: the ctor allocates the 32x32 holder, `imageWidth`/`imageHeight` read the bitmap (throwing `Not drawable layer type` only when the script freed it), and a render node dropped by `Invalidate`/KAG retargeting is rebuilt with its bitmap at the layer Rect. Host diagnostics: high-frequency lifecycle logging (WaveSoundBuffer/KAG audio, KAG tag dispatch) is categorized and gated by the `KRKR_TRACE` env var (`audio,kag` or `all`), and calls into stubbed native methods are counted with a first-call warning.
- `krkr-plugins`: pure Rust plugin registration.
- `krkr-core`: pure Rust shell/runtime state, input events, view models, draw lists, layer tree, message layer model, image upload metadata, and audio command model. No platform UI or GPU APIs.
- `krkr-render`: `wgpu` rendering, surface/device/pipeline management, rectangles, uploaded textures, text texture presentation, clipping, content sizing, and transitions.
- `krkr-font`: font discovery, metrics, glyph rasterization, and RGBA text image generation used before GPU texture upload.
- `krkr-platform`: filesystem and minimal platform bridges. Keep native UI out of core and avoid platform UI components for engine surfaces.
- `krkr-audio`: Kira/CPAL audio backend for static/streaming playback, buses, volume, fade, pause/resume, and stop commands. Also plays live PCM streams (`AudioCommand::PlayPcmStream`) fed by external decoders — movie soundtracks arrive this way; video containers never go through the audio file loaders.
- `krkr-xp3`: XP3 archive parsing and resource streaming.
- `krkr-video`: video decoding behind a `VideoDecoder` trait with per-platform pluggable backends. The platform's own decoder is primary wherever one is compiled in: AVFoundation/VideoToolbox on macOS (feature `macos-avfoundation`), plus the Android MediaCodec / iOS AVFoundation / Web media-element profiles for the shells that provide them. Where a host has no system decoder, the opt-in `ffmpeg` feature supplies an **embedded** FFmpeg: `ffmpeg-next`'s `build` feature makes `ffmpeg-sys-next` clone FFmpeg `release/9.0`, configure it, build it from source and link the static libavcodec/libavformat/libswresample/libswscale archives into the artifact, so the shipped binary carries its own decoder and needs no system FFmpeg at build or run time (no pkg-config probe, no shared libav*, and the `ffmpeg` CLI is never invoked). The vendored configure line is FFmpeg's LGPL default — `--disable-gpl --disable-version3 --disable-nonfree`, `--disable-autodetect` (no external codec libraries), static + PIC + pthreads, only avcodec/avformat/swscale/swresample, `-O3` — and a direct `ffmpeg-sys-next` dependency pins `build-portable` so the artifact does not inherit `-march=native`; building it needs network (shallow git clone), a C toolchain (gcc/clang, make, nasm) and libclang for bindgen, takes ~3.5 min on a 32-core host and is cached per profile afterwards (the one-command reproduction and the `ldd` check live in the `crates/krkr-video/src/ffmpeg.rs` module docs). `crates/krkr-engine` enables the feature for Linux/Windows targets, so those builds select the embedded decoder; the mobile shells and Web keep their own paths until their FFmpeg cross-builds land. Selection is compile-time and exclusive — macOS keeps AVFoundation even when both are enabled — and `platform_capabilities()` reports exactly what `create_decoder()` on the same build returns. The backend reads `VideoSource::Bytes` through a custom in-memory AVIO (no temp files) and serves both sources equally. Delivers RGBA frames with PTS to the engine's VideoOverlay, and decodes the soundtrack (`audio_spec`/`next_audio_chunk`) into interleaved f32 LPCM that the engine streams to krkr-audio; `seek_ms` restarts the demuxer at the keyframe before the target and drops the pre-target frames/chunks so callers resume at (approximately) the requested position.
- `krkr-emote`: E-mote motion adapter over the vendored eluna fork (`vendor/eluna`: pinned at `12e4d2f`, excluded from our workspace and consumed as a path dependency, with provenance, the MPL-2.0 licence texts upstream's manifest declares, the pruned player and the two test-only patches recorded in `vendor/eluna/UPSTREAM.md`). Loads PARQUET's `.mtn` motions (PSB v3/v4) through eluna's parser with the source-table flavour normalised in-adapter (`src/normalize.rs`; no library code is patched), exposes sources/animations/layers/frames plus the sampled draw list (`Motion::draw_list`), decoded icon pixels (`Motion::texture_pixels`, M2 `RL` run-length and palettes in `src/decode.rs`) and a software rasteriser for the draw list (`src/render.rs`), and is wired into the engine through `crates/krkr-plugins/src/motion_player.rs` (the `Motion` / `Motion.Player` / `Motion.EmotePlayer` / `Motion.ResourceManager` / `Motion.SeparateLayerAdaptor` surface, with `emoteplayer.dll` installing the same one; physics, timelines, mesh deformation, particles, separate-layer mode and `.psb` model playback are registered stubs that warn once) — verified against the game's 23/23 `.mtn` files.
- `apps/debugger`: `krkr-debug` headless CLI combining an LLDB-style interactive script debugger (stdin REPL over the tjs2 debugger core; TJS2 + KAG breakpoints, stepping, exception breaks, expression eval) with batch probing (screenshot/pixel/layer dumps, at-frame script injection, synthetic clicks and `--move` cursor rest so hover states can be probed without activating a control, virtual clock/audio). Probing also works at the game's own KAG level instead of in screen coordinates: `--kag-state` logs transitions of the game's `kag` object (storage/label/line, conductor status, wait keys) and `--kag-click` performs a semantic click that wakes whatever the conductor is waiting on. `--trace` enables the engine trace categories, and every run ends with a summary of which stubbed native methods the game actually called. Native calls are the boundary where a script value becomes engine geometry, so the console can arm per-method call tracing on a live session (`trace add Layer.affineCopy`, or `--trace-call` from startup) instead of requiring an engine rebuild — a rebuild throws away a session that may have taken a hundred thousand frames to reach. The command set, dump helpers and software compositor live in the `krkr_debug` library (`console`, `snapshot`, `cli`) so the windowed `krkr-desktop --debug-console <fifo>` shell can embed the exact same console while a human plays. See `docs/DEBUGGING.md` for the investigation playbook.
- `apps/disasm`: `krkr-disasm` standalone TJS2 bytecode disassembler. Dumps full structured disassembly (data pool, object headers, data slots, instructions) of official `TJS2100\0` bytecode from loose files, XP3 members, or game directories (engine archive priority), and of krkr's own compiler output from TJS source.
- `apps/decomp`: `krkr-decomp` standalone TJS2 bytecode decompiler. Reconstructs readable, recompilable TJS2 source from official `TJS2100\0` bytecode (loose files, XP3 members, game directories, or krkr's own compiler output via `--source`); `--verify` reparses and recompiles the output, and unhandled bytecode fragments appear as `// <unhandled: ...>` comments counted in the run summary.
- `apps/desktop`: `winit` app lifecycle, input mapping, launcher/settings/runtime state transitions, renderer/audio integration, project selection, and fullscreen/window sizing. `--debug-console <fifo>` attaches the shared `krkr-debug` console to the live window: an agent writes commands to the FIFO and reads dumps from stdout while the player drives the game, which is the fastest way to inspect a scene that takes a long time to reach. Launch it from the repo's dev shell, `nix develop --command cargo run -p krkr-desktop -- /path/to/game`, because winit and wgpu load their Wayland, xkbcommon and Vulkan libraries with `dlopen`, and the shell is what puts those on `LD_LIBRARY_PATH`.
